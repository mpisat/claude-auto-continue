# Project review and macOS remediation

Reviewed the fork at `4f84cf6181d29416b13df16591b3abbf39fac812`, then reviewed the macOS remediation in the dirty working tree based on that commit on `macos-multi-session`. Scope: native macOS core, Accessibility adapter, menu app, controls and installers; inherited Bash CLI, hooks, CI, Windows helpers and legacy macOS scripts. The owner approved the foreground fallback and subsequently said, “Review and fix macOS defects.” Remediation covers the installed native macOS application. The inherited implementations below remain separate, unmodified implementations.

The native macOS code has passed the checks below, but unattended recovery after the next real reset remains unverified. The full fork is not release-ready: the inherited CLI and Windows findings remain open. Both installed helper services are intentionally stopped during a separate repeated-character incident in Claude's Code composer.

## Native macOS findings addressed

The following defects were reproduced or verified against the production source and fixed. Regression tests were observed failing before the corresponding fix, then passing.

| ID | Severity | Finding and resolution |
| --- | --- | --- |
| M1 | P1 | The watcher installer suppressed unload errors and could delete its bundle/plist while it continued running. Both installers now stop on inspection/unload failures, verify absence before replacing/removing files, and accept only launchctl exit 113 as absence. |
| M2 | P2 | Reinstall after documented Stop could fail because launchd's persistent disable flag remained set. Installation now explicitly enables before bootstrap. |
| M3 | P2 | Menu commands could hang beyond their deadline while a child retained stdout or ignored termination. Commands now have independent bounded completion, a bounded 64 KiB output read from a private regular file, a dedicated owned process group cleaned before reaping, and invocation IDs that reject stale callbacks. |
| M4 | P2 | The menu disabled Stop for loaded, unhealthy or crash-throttled jobs. Stop now remains available for installed stopped jobs. |
| M5 | P3 | Raw duplicate session arguments overstated monitored-session counts. Installation and status reporting now deduplicate IDs. |
| M6 | P3 | Packaged Instructions began with a checkout-specific path that failed after source relocation. They now lead with the installed bundle's controls and distinguish source-only build operations. |
| M7 | P2 | A final transcript veto/read error after persisting intent left a definitely-unsent attempt permanently pending. The coordinator now records notSent with the existing count/backoff; a failed recovery save conservatively retains the pending fence. |
| M8 | P2 | Makefile status/stop/start/menu treated inspection errors as absence; Stop could report OFF while the job remained loaded. Inspection failures now propagate with their diagnostic, including inside transition polling. |
| M9 | P2 | An unknown current chat identity bypassed the current-composer draft guard. Drafts now block navigation regardless of whether the current identity is known. |
| M10 | P2 | AX messaging timeout was set only on the application object, leaving descendant reads and actions at the default timeout. It is now set through the system-wide AX object, which Apple's installed SDK defines as this process's default. |
| M11 | P3 | Action failures/vetoes logged stale preparation diagnostics such as ready. Per-session diagnostics now follow the actual Retry action result and explain vetoes, uncertain outcomes and failures. |

M1–M8 map to the changed installers, Makefile, ClaudeMenu sources and ResumeCore coordinator. M9–M11 map to DesktopAX/Desktop.swift. Tests live in `tests/test-macos-controls.py` and the native package's corresponding test targets. No credential, plan, subscription or native Claude auto-continue setting was changed.

## Approved foreground fallback

The 11:50 Bangkok reset on 2026-10-25 exposed navigation failure: at 11:52:27 both due sessions logged blocked_wrongIdentity. A later Retry action at 11:53:44 was followed by assistant progress, which the helper confirmed at 11:54:32; the other affected chat resumed without a helper Retry. This does not establish five-session unattended success or identify the exact cause of the first failed selection.

After wrongIdentity or unavailable navigation, the updated adapter may bring the existing Claude application to the foreground, verifies activation, and retries navigation once. Busy chats, drafts and already-resumed chats do not trigger this fallback. Identity, transcript and persistent attempt checks still precede Retry. Activation may itself wake native auto-continue, so its new state is checked again.

A controlled read-only foreground diagnostic selected the exact target and restored the original conversation. The owner left Claude untouched during this test. No Retry was pressed and no message was inserted. Earlier tests during concurrent manual chat changes were inconclusive. Foreground activation is a mitigation; the next real reset remains the acceptance gate.

`diagnose --foreground` explicitly exercises foreground navigation without pressing Retry. The flag is restricted to diagnose.

## Unresolved questions and live gates

- The original background navigation failure's exact cause is not proven. Concurrent manual selection can invalidate navigation observations; the controlled foreground test passed. A real unattended reset is still required.
- The owner reported repeated characters only in Claude's Code composer. It persisted with both custom helpers stopped; normal Chat and other applications were unaffected. This does not rule out persistent Accessibility state. A clean restart/test is deferred because current Code work is not safe to interrupt. The updated helpers remain stopped and UI inspection is paused.
- [OpenAI issue 55925](https://github.com/openai/codex/issues/55925) describes a similar pattern during agent control of Claude. [Screenpipe issue 3884](https://github.com/screenpipe/screenpipe/issues/3884) documents Accessibility-related input replay in Chromium/Electron. These reports support a hypothesis, not attribution of this incident to a specific component. The custom native implementation has no keyboard-injection, clipboard or AXEnhancedUserInterface/AXManualAccessibility toggle calls.
- Assistant-progress confirmation does not pin a transcript position/timestamp. Replacing a transcript with historical assistant output can synthetically produce a false confirmation; no normal Desktop operation producing that rollback was established. This is an unresolved caveat, not a verified production finding.
- The updated signed helper bundles were installed without launching; plists and attempt ledger were unchanged. Their background Accessibility permission has not yet been revalidated after the rebuild.
- Keeping native auto-continue enabled alongside the helper cannot provide atomic exclusion between those independent senders. The owner chose to keep it enabled; the grace period and revalidation reduce overlap.

## Verification and release assessment

- 76 native tests passed: 38 core, 26 Accessibility, 12 menu tests. Parameterized cases additionally cover rejection states.
- 17 isolated production-control/installer tests passed, including permission/transport errors, absent jobs, unload failure/timeouts, disabled reinstall, duplicate arguments, preserved state, and hung child processes.
- Existing CLI suite: 31 passed. The open CLI findings above show why that suite alone is insufficient evidence of correctness.
- Separate specification and code-quality reviews found no remaining actionable concern in the native macOS remediation. These are bounded review results, not proof that all possible defects have been eliminated.
- No Cloudflare validation, real model fixtures, credential-store changes, plan/subscription changes or Windows live automation were performed. Source and shared native preferences are preserved.

P1 inherited findings L1, L2 and U1 block trusting those implementations for unattended use. The native macOS remediation is suitable for the next controlled validation after input is healthy and updated Accessibility permission is confirmed. It is not yet verified as unattended five-session recovery, and the whole fork is not being declared perfect or release-ready.
